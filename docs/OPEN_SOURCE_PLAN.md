# KindleGlance · Kindle 看板：开源改造规划

状态：M0–M4 软件候选版已实现；真机与生产副本验收未完成，结果以 IMPLEMENTATION_STATUS.md 为准。审视基线：本地 `main` 的 `4c5d4bb`；2026-09-27（北京时间）。

目标：让一个没有作者现场配置、没有作者账号和服务器权限的人，从公开仓库独立部署，在管理页面完成首次设置，并把自己的 Kindle 连接成可长期使用的信息看板。

项目名确定为 **KindleGlance · Kindle 看板**，建议公开仓库名 `kindle-glance`。已授权公开 GitHub 候选版发布；生产服务不变。

## 1. 范围与既有讨论

用户已明确：去掉默认厦门的个人化假设；地点和时间可在管理端修改；首次进入管理页面提供类似手机首次开机的分步设置；开源前全面整理。

已经找到的相关历史依据：

- [贡献指南](../CONTRIBUTING.md)、[第三方说明](../THIRD_PARTY_NOTICES.md)：已整理源码、测试、构建白名单、私有文件忽略规则及第三方许可。现有仓库整理是起点，但还没有形成面向陌生用户的安装产品。
- 独立运行研究（历史资料）：讨论过脱离 KOReader、图书馆入口、专用启动器和原生显示/电源适配。研究资料保留在本机历史档案，不属于首版实现。
- [启动入口说明](../kindle-launcher-ab/README.md)、刷新研究（已暂停）：正式 B 入口、一键开始仍是后续项；同图零刷新、合并刷新实验已暂停，不应借开源整理恢复未验收功能。
- 历史配置要求看板使用上海时间，管理浏览器可以保留其他时区。这应成为迁移测试场景：浏览器时区不得悄悄覆盖看板时区。

在本次读取的文档和聊天范围内，没有找到已定稿的完整开源规划或首次设置方案。因此下面保留结合既有结论形成的规划，不把建议写成以前已确认的需求。

**首版边界建议**：自托管、单管理员、一个全局看板配置和播放列表；设备支持继续以 Paperwhite 5／KPW11、现有 KOReader 基线为准。其他设备标明未验证。多用户、多设备独立播放列表、完整英语界面、原生独立客户端进入后续版本。

## 3. 首次设置：用户实际会经历什么

### 3.1 入口与完成标准

首次打开 `/admin`，先证明具有初始化权限，再进入向导。初始化状态保存到服务端，不能以浏览器 localStorage、Cookie 是否存在或清缓存来判断“首次”。后续浏览器登录直接进看板；设置页可随时修改之前的选择。

建议用安装脚本生成一次性初始化码和独立内部密钥，将初始化码写入受限本地文件，由安装者主动查看。初始化码有有效期，可通过本机命令重发；管理员建立后立即作废。不能采用“第一个打开公网网页的人就是管理员”。已有管理密码的升级实例继续正常登录。

| 步骤 | 用户看到和完成的事 | 可跳过范围 |
| --- | --- | --- |
| 1. 欢迎与管理员 | KindleGlance 名称、一句话用途；凭初始化码设置管理密码 | 新部署必须建立管理权限；不要求注册第三方账号 |
| 2. 你的地区 | 搜索城市，选择“城市／省州／国家”；展示当地当前时间与时区，确认看板所在地 | 地区和时区必须明确确认；可手填坐标，不强制浏览器定位 |
| 3. 选择内容 | 推荐天气、日历、年度进度等，勾选后看到第一张看板预览 | 高级内容以后添加；Codex 不进入基础必填步骤 |
| 4. 连接 Kindle | 显示实际可达服务地址、设备令牌和安装步骤；等待第一次鉴权成功的设备取图 | 允许“稍后连接”，保留待连接提示 |
| 5. 完成 | 汇总地点、当地时间、内容和设备状态；进入日常管理 | 无设备时仍可完成服务端设置与预览 |

时间格式、温度单位和一周起始日放在地区步骤的展开选项中；刷新间隔与省电说明放在设备步骤，不一次展示一屏技术参数。首版只展示已经实现的选项。

### 3.2 地区选择规则

- 搜索支持中文和英文，同名城市必须显示国家与行政区；选择后保存稳定地点标识、展示名称、经纬度和 IANA 时区。
- 可使用 Open-Meteo 地名搜索，其结果提供经纬度、行政区及 IANA 时区；保留手动输入入口以应对地名缺失或搜索服务不可达。[官方地名 API](https://open-meteo.com/en/docs/geocoding-api)
- 城市决定默认时区，用户可以显式改选。浏览器时区仅作建议，不自动覆盖；不根据 VPS IP 推断用户位置。
- 默认不请求精确定位；若以后提供“使用当前位置”，由用户主动触发，并解释会向天气服务发送坐标。展示城市级信息即可，无需保存住址。
- 搜索走服务端固定服务域名，做长度限制、超时、缓存和请求节流；不开放任意 URL 代理。
- 城市搜索失败可继续手动设置。首次天气失败展示“天气暂不可用”及重试，不编造天气，也不回退成厦门。

### 3.3 交互与视觉原则

使用场景是用户刚部署完容器，拿手机或电脑把闲置 Kindle 配好。体验应安静、明确，每一步有一个主要操作，并且看得见自己离成功还有多远。

- 延续当前管理端的深色背景、绿色操作色与清晰表单层级。墨色、纸白、石灰、雾灰和现有绿色构成配色依据；设备预览保持真实灰阶。
- 以纸张、墨水、日照、当地时间、轮播、省电为界面内容依据。显著元素是“随着地区与内容选择更新的真实看板预览”，而不是装饰插画。
- 避免把环境变量表单搬成第一屏、把所有可选集成都设为必填、把大量指标卡塞入向导。桌面可并排显示步骤与预览，手机按阅读顺序纵向展示。
- 上一步不丢输入；刷新、网络中断和关闭页面后可续设；提交有加载、失败、重试和完成反馈。
- 保留键盘操作、明确焦点、关联标签、错误提示和足够触控面积；尊重减少动态效果设置。具体组件尺寸和动效在实施时验证，不在规划阶段伪称已完成视觉验收。

## 4. 配置与时间：先统一底层，再做表单

### 4.1 配置职责

建议新增 `settings.py` 与版本化 `settings.json`，沿用现有 JSON 状态方式和单进程运行约束。首版无需为了向导引入数据库。管理员凭据和初始化凭据单独存储，密码使用适合密码的单向哈希；不进入普通设置导出。

| 层级 | 内容 | 管理方式 |
| --- | --- | --- |
| 部署配置 | 数据目录、监听地址、可信反向代理、内部服务地址、密钥路径 | 环境变量／secret 文件；不放普通页面表单 |
| 全局看板设置 | 地点、时区、显示偏好、设备档案、对设备公布的基础地址、初始化状态 | 管理页面修改，持久化并带版本/修订号 |
| 项目设置 | 名称、方向、播放时段、时长、山水风格、账号栏位的手工信息 | 保留当前具体看板的项目设置入口 |

建议全局结构至少包含 `schema_version`、`revision`、`setup_state`、`location`、`timezone`、`display_preferences`、`device_profile`。`setup_state` 区分未初始化、设置中、已完成、迁移后待确认；缺失和文件损坏不可等同处理。

配置优先级必须明确：显式部署锁定值 > 已保存设置 > 仅用于未设置项目的默认值；旧 `WEATHER_*` 和 `TIMEZONE` 首次迁移导入后不再隐式覆盖 UI。若需要保留环境强制覆盖，用明确的锁定机制，并在页面标明不可编辑及来源。

### 4.2 生效与缓存

1. 服务端校验名称长度、坐标范围、IANA 时区、选项枚举、地址格式；无效数据返回字段错误，保留旧设置。
2. 用修订号检测两个浏览器同时保存，冲突时要求刷新；写入使用锁和原子替换。一次渲染使用同一份不可变配置快照。
3. 把相关配置摘要放入天气、页面图片和传输图片缓存身份。地区/时区改变后，所有受影响页面和当前预览及时更新。
4. 保存配置时正在进行的旧渲染不能覆盖新修订；旧城市缓存不能作为新城市的失败兜底。保留最近成功图时必须标明它属于旧配置，不能改标题伪装成新城市。
5. 不依赖重启容器才生效。页面显示“已保存／正在更新预览”，并区分服务器生成成功与设备已取图。

首版采用一个全局地点。现在渲染锁和页面缓存主要按 `page_id` 组织；若以后同一个天气模板可放两个城市，应先改为包含项目/配置的缓存身份，否则会串图。多地点属于后续扩展。

### 4.3 全链路时间规则

- 数据中的采集、重置、订阅到期、登录失效等保存 UTC 时间戳；展示与用户输入使用所选看板时区。地区变更不重新解释既有时间戳。
- 管理首页、播放时间段、天气日期、日历、年度/时间进度、昼夜信息、山水换景和账号页必须使用同一配置上下文。
- 订阅输入移除前端 `+08:00` 算法，提交“当地日期时间 + IANA 时区”，由服务端转换。夏令时不存在的时间要拒绝，重复时间要明确偏移或让用户选择，不能静默偏移一小时。
- 保留“订阅到期时间为人工维护”的数据含义；不拿额度重置时间推算。现有到期时间戳原值迁移，上海用户看到的日期保持不变。
- 播放时段以看板当地墙上时间匹配；UTC 时间推进时，夏令时跳过的当地时段不补播，回拨重复时段按当下匹配重新评估。文档明确该规则。
- 24 小时制、周起始日、摄氏/华氏可做设置，但要真正贯穿页面。当前月历周日起始、时间刻度周一起始，需统一决策；单位切换同时更新温度数值、标签和缓存，不能只改符号。
- 第一轮先完成地点和时区；显示偏好可在首版发布前的第二轮补齐。英语界面另行排期，中文首版应明确语言支持范围。

## 5. 已有实例迁移

现有 VPS 是已配置用户，不能因为没有新 `settings.json` 就进入空白向导，也不能因开源改造重置播放列表和设备令牌。

迁移流程：备份 → 识别既有状态 → 导入旧环境配置 → 校验 → 原子写入新设置 → 记录迁移版本 → 对照验收。已有播放列表、账号绑定、手工到期时间、图片方向和刷新策略原样保留。

- **全新空目录**：没有地区隐式默认值，进入首次设置；配置前服务不请求厦门天气，设备接口返回可识别的“尚未完成设置”状态。
- **完整旧配置**：一次性导入城市、经纬度和时区，标记完成；正常登录后显示一次迁移摘要，可进入设置修正。
- **旧实例依赖代码隐式默认值**：为维持当前使用，迁移成明确的旧默认配置并提示确认；不能把同样默认值用于全新安装。
- **部分配置缺失或损坏**：保留原文件和可用画面，进入修复流程；不按“新用户”覆盖数据。
- **重复运行迁移**：幂等；不重复加页面、不重新生成现有凭据、不覆盖已修改的新设置。
- **回退**：保留旧镜像与迁移前数据备份，写明回退步骤；验证旧程序能否读取升级后的其他状态文件，不能只承诺换回镜像即可。

账号设置仍保留在“用量提示”的项目设置里。新增全局“设置”入口负责地区、设备连接和管理维护，不把同一份账号资料复制到向导或全局设置形成两套来源。

## 6. 可独立部署与可选集成

### 6.1 基础安装

- 提供从干净目录启动的 Compose；使用项目自建网络和持久卷，解决 UID 10001 写权限；首次安装不要求预先存在作者的外部网络。
- 提供自动生成独立随机密钥的初始化命令，检查占位值；不要要求新用户手工编造四组密钥。增加 Python 跨平台工具或明确 Linux/Windows 等价步骤。
- 示例域名统一改为文档保留域名/明确占位值，默认地点留空。所有参数集中列出默认值、是否敏感、修改生效方式。
- 默认构建不硬依赖国内镜像，国内加速作为显式可选参数；固定已验证依赖与镜像基线，给出更新路径。
- 分开写局域网与 VPS HTTPS 两条安装路径；说明设备必须能访问图片基础地址。反向代理信任范围、Cookie Secure 与外部 URL 要一致，不盲信客户端 Host/转发头。
- 初始管理页面在慢网络或 Chromium 不可用时仍可打开；按需生成首屏，后台进行其余渲染，区分存活、就绪和内容数据失败。
- 继续一个 Uvicorn worker；先给出实际测试的资源占用，再发布最低配置建议，不凭经验编造内存门槛。

### 6.2 Codex 用量作为可选组件

- 用 Compose profile 或单独覆盖文件启用采集器；提供 Dockerfile、固定并验证的官方 CLI 版本、状态卷、只读展示卷和内部 secret 接线。
- 基础安装不连接作者账号、不要求 Windows/Cockpit、不要求安装 CLI、不默认轮播空账号页。关闭模块后不轮询不可达采集器。
- UI 清楚区分“功能未安装”“已安装未授权”“已授权待同步”“同步异常”。旧数据源切换文案只在迁移场景出现。
- OAuth 凭据只保存在采集器私有卷。展示快照虽然没有凭据，仍可能包含邮箱、套餐和额度，不能当作适合公开下载的数据。
- 增加公开截图/诊断用的虚构数据；提供可选邮箱遮罩，但迁移保持当前用户完整显示邮箱的选择。
- 说明授权、重新授权、解绑、备份、删除与故障处理；升级 CLI 时跑协议兼容测试。人工订阅日期继续显示来源，不承诺自动读取。
- `tools/cockpit-sync` 标为历史兼容工具，不出现在新用户推荐安装链路。

### 6.3 天气外部服务

首版继续使用现有 Open-Meteo，集中 provider 边界以便日后替换，不先建立复杂插件市场。完善超时、缓存、过期提示和服务不可达状态。

公开安装文档需说明天气与地名查询的外部数据流、来源署名及使用条件。Open-Meteo 当前免费服务限非商业使用并有请求限制，不能把项目代码开源等同于所有使用场景都可无限免费调用；商业部署另按其服务方案配置。[官方使用条款](https://open-meteo.com/en/terms)

## 7. 设备、安全与公开资料

### 7.1 设备交付

首版整理正式“KindleGlance · Kindle 看板”入口与安装文档，A/B 实验名称移入历史说明。先改变用户可见名称，谨慎保留 `trmnl.koplugin`、设置键和现有 API 契约；如改目录名，必须提供升级与卸载迁移，避免两个插件同时加载。

设备连接页至少支持查看/复制服务地址、受控显示令牌、令牌轮换与最近鉴权取图记录。首版手动配置可交付；短期配对码可在随后优化，不能只靠一个手机二维码宣称 Kindle 能自动配对。设备端间隔目前可独立设置，与服务端建议间隔需写明关系。

建立设备矩阵，分别记录机型、固件、KOReader、方向、退出恢复、RTC、深睡与续航测试。只有真实验证的组合标“已支持”，请求里携带尺寸或能够缩放图片不等于完整适配。原生独立客户端、一键启动、图书馆入口单独里程碑，不阻塞基础开源版本。

### 7.2 发布前安全门槛

- 修复插件元数据和图片下载的 TLS 证书校验，核查 CA、设备时钟、主机名验证和重定向行为；自签证书仅通过明确导入信任等方式处理。若尚未完成，不宣称公网连接已安全，限制该版支持范围并明确风险。
- 新装初始化防抢占；管理登录限速；设置、重置、导入、令牌操作继续做鉴权和 CSRF；密码/会话密钥变更使旧会话失效。
- 初始随机设备令牌、图片签名和会话密钥相互独立；保留旧设备升级的过渡方式，不突然让已部署 Kindle 失联。
- 扫描 Git 全历史及所有分支/标签、源码、预览图片、示例包和发布附件。`.gitignore` 不会消除已入历史的信息；检查真实域名、邮箱、网络地址、用户名、机器路径、日志和凭据，不只查 `.env`。
- 扫描报告脱敏；发现真实凭据先撤销/轮换，再决定净化公开历史或建立经过审查的公开基线。保留本地私有恢复档案，不在规划阶段重写历史。
- 备份分为可分享的非敏感配置导出与包含凭据的管理员完整备份；诊断导出默认去掉邮箱、令牌、授权码、签名 URL、Cookie 和私有路径。

## 8. 实施顺序与验收

以下按依赖排期，不给未经拆分验证的工期承诺。每轮有独立交付物，功能完善后再进行线上迁移。

| 阶段 | 工作 | 完成门槛 |
| --- | --- | --- |
| M0：公开基线准备 | 名称/目录策略、全历史与资产审查、许可清单、通用部署草案 | 公开材料范围清楚；不包含作者运行数据；迁移前备份与回退方案明确 |
| M1：配置底座 | `settings.py`、版本化持久化、旧环境导入、统一地区/时区、缓存修订 | 改城市和时区无须重启；不串旧图；既有上海实例行为保持；迁移可重复和回退 |
| M2：首次设置与日常设置 | 初始化权限、向导、城市搜索/手填、预览、设备连接、全局设置入口 | 全新目录可完成流程；刷新续设、失败恢复、手机操作、无设备完成均通过 |
| M3：通用交付 | 干净 Compose、可选采集器、TLS、正式入口、显示偏好、用户文档 | 陌生用户无需作者现场信息即可安装；未启用可选集成也正常运行；公网安全门槛满足 |
| M4：发布候选 | CI、端到端安装/升级/备份恢复、公开包与截图审查、真机回归 | 发布检查清单全部满足后创建公开发布版本 |
| 后续 | 多设备/分辨率、多城市项目、英语界面、配对码、一键入口、独立运行 | 各自设计和验证，按需求进入独立迭代 |

建议首先实施 **M1：配置底座 + 旧数据迁移 + 地点/时区设置**，然后接 M2。M0 的公开材料审查可以先完成；不要先堆向导界面，再发现保存后的配置无法被所有模块使用。
